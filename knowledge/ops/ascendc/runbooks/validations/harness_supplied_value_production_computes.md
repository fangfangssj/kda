# 测试 harness 里写死、而生产环境会计算的入参，是注入缺陷

## 适用场景

- 工程形态：手工新增 dtype、手工移植算子，或任何**不经托管 op-gen 管线**而自建 golden、输入与调用的验证工程。托管管线会提供元数据与输入构造，手工路径不会。
- API 路径：`aclnn*GetWorkspaceSize` 的元数据或描述类入参；在生产中由独立算子计算、而测试里被常量替代的任何张量。
- 验证过的平台与 CANN 版本：Ascend950DT_9582 / CANN 9.2.0。
- 适用粒度：`platform_wide`，与具体算子无关，任何自建 harness 都适用。
- 路线优先级：`required_precondition`，应在构造任何判别实验**之前**执行。
- 明确不适用或未验证场景：经 op-gen 托管生成的验证工程（元数据由管线提供）；纯推理调用、不构造反向元数据的场景（未验证）。

## 结论

**在把任何失败归因于被测算子之前，先枚举 harness 供给、而真实调用方会计算的每一个值。** 测试代码里的字面量出现在生产有计算的位置，不是简化，是**缺陷注入**；它产生的失败与算子自身缺陷在观测上不可区分。

## 为什么常规防护抓不到

所有下游对照都**共享**这个错误激励，因此一致通过：

- 重复运行复现同一常量；
- 正对照与负对照（如全零向量对照）同样建立在该激励上；
- 独立重算 golden 只验证参考路径，不验证刺激；
- 跨主机桥接对照同样共享；
- 定量吻合会**加强**错误结论：实例中预测 eco 0.5845 对实测 0.5846，四位小数吻合，它确认的是作者对自己缺陷的模型。

仪器可以完全正确而指向一个虚构。**上游的严谨不会发现下游的跳跃，反而为它背书。**

## 判据与操作

1. **失败边界落在与形状无关的常数上**时提高警惕。实例中「正确切片数恒为 32，跨 B·N 四倍范围、所有 S 与 D 都不变」被当作「不随任何量缩放，所以不是容量效应」的证据；实际上「不随任何量缩放」更可能说明**这个数是测试方自己供的**。
2. 检索 harness 中传入 API 的字面标量，逐个问：**生产里谁计算它，我调用了吗？**
3. 若算子源码中存在**定义了却从未被调用**的计算函数，它通常正是生产中由外部提供的那个量的参考实现，可用来校正 harness。实例中 kernel 内的 `cal_deter_max_loop_num` 即是。
4. 对每个可疑供值做**扫描**而非取单值：饱和说明不是该值限制，随之变化说明是。
