# ST 批跑 507014 偶发与状态连带：隔离重跑判别

## 现象

自定义分组矩阵乘算子迭代三全量 C++ ST 测试（687 条 = 37 条 L0 基线 + 650 条 L1 全场景，Real NPU 模式，真实 NPU vs CPU golden 逐输出比对）首跑 684/687。3 条失败呈特殊模式：

- L1-0153（M=4 unequal transpose, fp16, si=2）与 L1-0348（E boundary E=4 si=0 bias=none, fp16）报：

```text
[L1-0348] E boundary E=4 si=0 bias=none
  M=64 K=64 N=64 E=4 dtype=float16 split_item=0 tw=false bias=no(none)
  [FAIL] 流同步失败: 507014
```

- 紧随 L1-0348 之后的 L1-0349（同 shape、仅 bias=yes(same) 配置不同）四个输出 tensor 全部数值错乱：

```text
[L1-0349] E boundary E=4 si=0 bias=same
  输出[0] shape: [16,64,] (1024 元素)
  [FAIL] MERE=1.31e+00 (>= 9.77e-04), MARE=1.34e+02 (>= 9.77e-03)
    不匹配 [0]: golden=-0.695801, actual=-0.408936, rel_err=4.12e-01
    ...
  输出[2] ...
  [FAIL] MERE=1.42e+00 (>= 9.77e-04), MARE=1.73e+02 (>= 9.77e-03)
```

单看 L1-0349 是典型"严重精度缺陷"信号（MARE 高两个数量级）；但它是紧跟流同步失败用例之后出现的。全量统计：L0 37/37、L1 647/650，流同步失败共 2 行。

## 适用场景

- 工程形态：C++ ST Real 模式批量测试（fork 子进程逐用例隔离执行）的结果解读与失败分类。
- API 路径：aclnn 流同步（错误码 507014 = ACL 流同步失败）；ST run.sh `--real --case <csv>`。
- 验证过的平台与 CANN 版本：Ascend950PR，CANN 9.1.0。
- 适用粒度：platform_wide。
- 路线优先级：recommended_fastpath（判别流程本身）。
- 明确不适用 / 未验证场景：隔离重跑仍失败的用例（那是真实缺陷，须走精度定位流程）；Mock 模式（无 NPU 执行，不会出现 507014）；偶发率统计（单次轨迹无法给出）。

## 判别方法

**第一步：失败分类。** 对批跑日志先按错误串分类，不要把"流同步失败"与"数值 mismatch"混为一谈：

```bash
grep -c "流同步失败" <st_raw.log>        # 流同步失败行数
grep -E "\[FAIL\] MERE" <st_raw.log>     # 数值失败行
```

**第二步：检查时空相邻性。** 数值失败的用例是否紧跟在流同步失败用例之后（本例 L1-0349 紧跟 L1-0348，仅 bias 配置不同）。相邻性是"状态连带"的关键信号。

**第三步：提取失败用例隔离重跑。**

```bash
cd operators/<op_dir>/tests/st && mkdir -p reports
head -1 testcases/iter3_full.csv > testcases/iter3_retry3.csv
grep -E "^L1-0153,|^L1-0348,|^L1-0349," testcases/iter3_full.csv >> testcases/iter3_retry3.csv
bash run.sh --real --case testcases/iter3_retry3.csv 2>&1 | tee reports/iter3_retry3.log
echo "EXIT_CODE=${PIPESTATUS[0]}"
```

（run.sh 本身按用例 fork 子进程，每条用例独立 aclInit/SetDevice/Stream 生命周期。）

**第四步：判读。** 隔离重跑全 PASS 且数值远低于阈值 → 判运行时偶发 + 状态连带；任一用例仍失败 → 真实缺陷，转入精度定位。

## 根因

批跑中偶发的 ACLNN 流同步失败（507014）是运行时/硬件瞬时态错误，不是算子代码缺陷；紧随其后用例的严重数值错乱是该失败的后遗症——前序用例 NPU 状态异常导致后续用例读到错误数据（状态连带），并非该用例自身的 kernel 精度问题。隔离重跑（独立进程生命周期）后同用例数值恢复正常证实了这一点。507014 偶发本身的驱动/硬件层机制未验证。

## 解决配方

本卡是判别规则而非代码修复：对批跑失败先做"错误串分类 + 相邻性检查 + 隔离重跑"三步，重跑通过即按偶发记录（retry 日志归档入 reports/），不创建算子缺陷 issue、不回退代码；有效通过率按"首跑通过 + 重跑通过"口径统计并如实标注（如 684/687 首跑 + 3/3 重跑 = 有效 687/687，验收报告中写明 3 条偶发与重跑证据）。

## 设计决策

- 采用"提取失败用例到独立 CSV 重跑"而非"全量再跑一遍"：全量重跑无法区分偶发与顺序相关缺陷，且耗时；最小用例集重跑直接回答"用例本身是否有缺陷"。
- 有效通过率口径保留首跑失败记录（684/687）而非静默覆盖：偶发证据链（原始日志 + 重跑日志）都要归档，供后续出现频率分析。
- 当前方案属 recommended_fastpath：批跑失败的第一响应动作。

## 验证信号

来源说明：以下信号来自该算子迭代三 ST 验收的全量日志分析与失败用例重跑记录（Ascend950PR，CANN 9.1.0）。

- 首跑：L1-0153/L1-0348 各 1 行 `[FAIL] 流同步失败: 507014`；L1-0349 四输出 MERE 最高 1.42e+00、MARE 最高 1.73e+02（阈值 9.77e-04/9.77e-03）（来源平台：950；证据等级：tool_observed）。
- 统计：L0 37/37、L1 647/650；流同步失败 2 行（来源平台：950；证据等级：tool_observed）。
- 隔离重跑 3/3 全 PASS：L1-0153 MERE=0.00e+00/MARE=0.00e+00；L1-0348 四输出 MERE≤6.72e-07、MARE≤6.88e-04；L1-0349 四输出 MERE≤1.09e-06、MARE≤9.17e-04；EXIT_CODE=0（来源平台：950；证据等级：tool_observed）。

## 失效边界

- 判别结论依赖"隔离重跑通过"；重跑仍失败即不适用，须按真实精度缺陷处理。
- 状态连带的传播范围未系统验证（本例观察到紧邻 1 条用例受影响；是否可能影响多条未测）。
- 507014 的触发条件（运行时长/负载/驱动版本）未知，无法给出规避手段；未验证，推断可迁移：其他 CANN 版本上 507014 语义应一致，但未实测。

**未决项**：

- 507014 偶发的机制层根因（驱动/硬件瞬时态的具体来源）未追——复现并追根因是优先接续项。
- 偶发频率与批跑规模/时长是否相关未统计（单次轨迹样本不足）。
## 坏实践

- 见到 L1-0349 的 MARE=1.73e+02 就直接进入 kernel 精度排查（查 cast/累加/搬运）：忽略相邻的流同步失败信号会把环境偶发当成算法缺陷，浪费整轮定位。
- 把 3 条失败用例从测试集删除或标记"已知问题"放行：丢失偶发证据链，且掩盖了需要观察的运行时行为。

## 误诊

- 初读 L1-0349 的四输出全 FAIL 时易判为"split_item=0 + bias 组合的精度缺陷"（其 shape/配置确属边界场景）；相邻性检查（紧跟 L1-0348 流同步失败）+ 隔离重跑数值正常，排除算法归因。
