# 确定性必须用张量原始字节度量，不能用 torch.save 文件摘要，且必须带扰动副本阳性对照

## 证据

三次独立的全量运行产生**三个不同**的 `.pt` sha256，而其中每个张量**逐位相同**：
`torch.save` 的 zip 容器内嵌非确定性元数据。harness 自身早已知道这点——
`pass_a_first_capture.py` 在保存时传 `_use_new_zipfile_serialization=False`
（`pass_a_artifact.py` 同）。

改在原始 `uint8` 张量视图上比较：**50/50 逐位相同**。

**通常被省掉的那一半**：把一份故意 +1 ULP 的扰动副本喂给同一套比较，**被检出**。

实测来源：run `142408a6-72e4-45a7-adea-1c83590452ff`（算子 48_GCModule），soc=Ascend950DT_9582，cann=9.1.0。

## 适用范围与边界

- 适用：任何算子的确定性度量（这是**方法**，与 kernel 无关）。
- **两个失效方向都实测到了**：文件摘要口径在逐位相同的数据上报"三次不同"（假阳性），
  而缺少扰动臂时"三次相同"与"比较器根本不会失败"不可区分（假阴性）。
  只报其中一臂的确定性结论不成立。
- **本卡不覆盖**非确定性的**根因定位**；它只约束**仪器**。根因分类另见确定性分析路径。

## 适用场景

- **工程形态**：三次独立全量运行的 .pt sha256 各不相同而张量逐位相同；zip 容器内嵌非确定性元数据，改用 uint8 视图。
- **验证过的平台**：Ascend950（以正文验证信号为准）。
- **适用粒度**：`operator_family`——与该卡所述 API/机制/缺陷族相同的场景。
- **不适用/未验证场景**：未在正文验证信号中列出的平台、dtype、shape 与该 API 变体；跨平台迁移须重新验证。
