# 归档完整性 ≠ 来源→二进制身份链（per-LEG，不是 per-archive）

## 核心结论

- 归档完整性校验证明的是"字节存得完整"，永远证明不了"这些字节产出了那个测量结果"。
- **source→binary 这条边只能在构建时刻锚定**，取自编译器自己的 depfile——下游任何东西都恢复不了编译器读了哪些字节。测量时的收据只能绑定测量进程 OPEN 的东西（映射的 .so、数据集、wrapper .py、profile），绑不到编译期输入；名字叫 source 的字段也可能指的是另一个 source。
- best-effort 的生产者强度 = 实际跑那条路径的 fail-closed 消费者的强度。手跑的 P/F 腿（管线外）两半都不触发。
- 降级证据"同 stage 目录 + 同构建分钟"**不是锚，且活不过归档**——归档会把成员 mtime 归一成 epoch 0。

## 实测锚点（4-44 归档审计）

精度收据的 wrapper 哈希吻合且有 before==after 二进制对；但供了被接受 geomean 的性能腿 `performance_g8.json` **零个 sha256 字段**，12 个 kernel 源文件哈希 0 个出现在 15 个证据文件里——诚实的措辞是"作为编译输入发货"，不是"编进了 DSO"。

## 判别规则

- 缺失的"存活字节的哈希"可补；缺失的"字节间关系"不可补。
- 同一张收据里 `geomean_speedup` 1.1059 与 `total_speedup` 0.9809 可以并存（同一 50 例，汇总口径不同）——**读两个聚合或都别读**。
- 历史归档不得绑定活判决（`valid: false`）；未被证据覆盖的正确性声明是永久不可证伪，不是"暂未验证"。

交叉：OL-510/OL-505/OL-515/OL-514/OL-509/OL-168（mtime 作漂移告警 vs 作身份锚，不矛盾）。

## 适用场景

- **工程形态**：归档完整性门只证明字节存得完整，永远不证明这些字节产出了那个测量结果；source→binary 边只能在构建时刻用编译。
- **验证过的平台**：a2、a3、Ascend950（以正文验证信号为准）。
- **适用粒度**：`operator_family`——与该卡所述 API/机制/缺陷族相同的场景。
- **不适用/未验证场景**：未在正文验证信号中列出的平台、dtype、shape 与该 API 变体；跨平台迁移须重新验证。
