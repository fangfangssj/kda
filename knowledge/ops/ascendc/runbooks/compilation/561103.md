# 561103 同名算子签名冲突链接绑内置版

## 适用场景

- **工程形态**：ops-registry-invoke 自定义算子开发，op_api 层调用 L0 API（`aclnnInplaceMaskedFillScalarGetWorkspaceSize`），测试程序动态链接 CANN 内置 `libopapi.so` 与自定义 `libcust_opapi.so`。
- **API 路径**：自定义 `aclnnInplaceMaskedFillScalar(value=const aclTensor*)` 与 CANN 9.1.0 内置同名算子（`value=const aclScalar*`）签名冲突。
- **验证过的平台与 CANN 版本**：Ascend950，CANN 9.1.0（`/home/developer/Ascend/cann-9.1.0`）。
- **适用粒度**：`platform_wide`——凡在 CANN 9.1.0 上注册与内置同名的自定义算子，只要测试程序链接顺序把内置库排在自定义库之前，都会命中。
- **路线优先级**：`recommended_fastpath`——调整 CMakeLists 链接顺序让自定义库符号优先解析（并允许多重定义）。
- **不适用或未验证场景**：a2/a3 未实测，推断 CANN 9.1.0+ 行为一致但未验证；自定义算子名不与内置同名时不触发；CANN < 9.1.0 若未内置同名算子也不触发。

## 判别方法

触发（tool_observed）：在 Ascend950 `masked_fill` 算子迭代一 ST Real 联调阶段，`bash run.sh`（`operators/masked_fill/tests/st`）退出码 1，grep 测试日志 `/tmp/st_real_output.log` 显示**全部 21 个用例返回 561103**（`aclnnInplaceMaskedFillScalarGetWorkspaceSize` 失败，`ACLNN_ERR_INNER_NULLPTR`），含本应通过的 FP16 同 dtype 用例——即不是 kernel bug，而是 op_api 链接/签名层系统性问题。安装算子包时还观测到（非 redacted tool_result 逐字保留）：

```
[ops_custom] [ERROR] Failed to load libcust_opapi.so wish env ASCEND_HOME_PATH(/home/developer/Ascend/cann-9.1.0),
error message is libcust_opapi.so: undefined symbol: _ZN4l0op10ContiguousEPK9aclTensorP13aclOpExecutor.
[ops_custom] [ERROR] Shared library validation failed. To skip this validation and continue installation, run this package again with --force.
```

探针（executable check）：

1. `find $ASCEND_HOME_PATH/include -name "*masked_fill*"`——确认 CANN 是否内置同名算子头文件（`aclnn_masked_fill_scalar.h`）。
2. `grep -rn "aclnnInplaceMaskedFillScalar" $ASCEND_HOME_PATH/include/`——读内置版本 `aclnnInplaceMaskedFillScalarGetWorkspaceSize` 签名，对比自定义版本的 `value` 参数类型（内置 `const aclScalar*` vs 自定义 `const aclTensor*`）。若两者类型不同即签名冲突。
3. `ldd <test_binary>` + `nm -D <test_binary> | grep aclnnInplaceMaskedFillScalarGetWorkspaceSize`——查符号解析路径，确认该符号绑定到 `libopapi.so`（内置）还是 `libcust_opapi.so`（自定义）。若先解析到内置版本即命中。
4. `find $ASCEND_HOME_PATH/lib64 -name "*.so" -exec sh -c 'nm -D "$1" 2>/dev/null | grep -q Contiguous && echo "$1"' _ {} \;`——定位哪个 `.so` 导出 `l0op::Contiguous`；若全库无导出（本 trace 在 cann-9.1.0/lib64 搜索未果），说明该符号未在当前 CANN 库集暴露。

观测（tool_observed）：步骤 1/2 确认 CANN 9.1.0 内置了 `aclnnInplaceMaskedFillScalar`，其 `value` 是 `const aclScalar*`（标量），而自定义版本 `value` 是 `const aclTensor*`（张量）——接口签名冲突。步骤 4 在 `cann-9.1.0/lib64` 全库未找到导出 `l0op::Contiguous` 的 `.so`，与安装时的 `undefined symbol` 报错一致。运行期全部 21 用例统一 561103，连 scope 内本应通过的 FP16 同 dtype case 也失败，排除 TilingKey/dtype 校验类根因。

判别与解释（interpretation，agent 根因分析，非 API 规范主张）：测试程序链接时 `libopapi.so`（CANN 内置）排在 `libcust_opapi.so`（自定义）之前被动态链接器解析，所有对 `aclnnInplaceMaskedFillScalarGetWorkspaceSize` 的调用都绑定到 CANN 内置版本。内置版本期望 `value` 是 `aclScalar`，但测试代码传入 `aclTensor`，内置版本内部 `l0op::Contiguous(selfRef, executor)` 对类型不匹配的 value 路径返回 `nullptr`，`CHECK_RET(selfRefContiguous != nullptr, ACLNN_ERR_INNER_NULLPTR)` 即返回 561103。`libcust_opapi.so` 加载时的 `undefined symbol: l0op::Contiguous` 是次生现象——自定义 op_api 调用了 `l0op::Contiguous`，但该符号在 CANN 9.1.0 的库集中未导出（或在不同库中），加载阶段即报错；用 `--force` 跳过校验继续安装只是掩盖加载错误，运行期全部 561103 仍会爆发。判别结论：凡自定义算子与 CANN 内置同名且签名不同时，必须让自定义库在链接顺序上先于内置库被解析（并允许多重定义），否则运行期会绑到内置版本并在签名不匹配处报 561103。

## 验证信号

来源：本 trace 在 Ascend950 / CANN 9.1.0 上对 `operators/masked_fill` 算子包做安装与 ST Real 联调；失败信号在 normalized trace 中以非 redacted tool_result 或工具执行（grep 实际日志文件）形式保留。

- 修复前：安装算子包报 `libcust_opapi.so: undefined symbol: _ZN4l0op10ContiguousEPK9aclTensorP13aclOpExecutor`（`Shared library validation failed`），非 redacted tool_result 逐字保留；`find cann-9.1.0/lib64 -exec nm -D` 全库未找到导出 `l0op::Contiguous` 的 `.so`。（来源平台：950；证据等级：tool_observed）
- 修复前：`bash run.sh` 退出码 1，grep `/tmp/st_real_output.log` 显示全部 21 ST 用例返回 561103（`aclnnInplaceMaskedFillScalarGetWorkspaceSize` 失败，`ACLNN_ERR_INNER_NULLPTR`），含 FP16 同 dtype scope 内应通过的用例。（来源平台：950；证据等级：tool_observed）
- 修复后（调整 CMakeLists 链接顺序使 `libcust_opapi.so` 先于 `libopapi.so` + 允许多重定义，`rm -rf build-real && bash run.sh` 重跑，grep `/tmp/st_real_output2.log`）：错误码从 561103 变为 161002（`ACLNN_ERR_PARAM_INVALID`，确认已调用自定义版本而非内置版本），FP16 mask 全 False / 全 True 用例 PASS。（来源平台：950；证据等级：tool_observed）

## 失效边界

- **未验证，推断可迁移**：a2/a3 平台推断 CANN 9.1.0+ 行为一致，但未实测。
- **不适用**：自定义算子名不与 CANN 内置同名时无此问题；CANN 版本 < 9.1.0 若未内置 `aclnnInplaceMaskedFillScalar` 也不触发。
- **设计层警告**：CANN 9.1.0 同时内置了 `aclnnInplaceMaskedFillTensor`（value=aclTensor），自定义算子若 value 是张量语义应改用 `-Tensor` 后缀避免冲突——这是设计阶段应规避的命名坑，本卡只覆盖运行期链接顺序判别。

## 坏实践

- 用 `--force` 跳过 `libcust_opapi.so` 加载校验继续安装——掩盖 undefined symbol，运行期全部 561103 仍会爆发。
- 修改测试代码把 `value` 从 `aclTensor` 改成 `aclScalar` 来「适配」内置版本——改变了算子语义，且无法覆盖 value 是张量的场景。

## 误诊

- 早期怀疑 `libcust_opapi.so` 的 `NEEDED` 缺 `libopapi.so` 导致 `l0op::Contiguous` 未定义——但测试程序直接链接了 `libopapi.so`（`ldd` 显示已加载），排除单纯缺库假设。
- 早期怀疑 `IsAiCoreSupport` 只支持 FP16 导致非 FP16 用例 561103——但 FP16 scope 内用例也 561103，且 561103 是 `INNER_NULLPTR` 而非 `PARAM_INVALID`（161002），排除 dtype 校验假设。
