# DataCopyPad / DataCopyExtParams are NOT SUPPORTED on dav-m200 (Ascend310P3), BOTH directions

**PB-105** — **`DataCopyPad` / `DataCopyExtParams` are NOT SUPPORTED on dav-m200 (Ascend310P3), BOTH directions** — SDK-header-level `ASCENDC_REPORT_NOT_SUPPORT` (CANN 安装树内 impl/dav_m200/kernel_operator_data_copy_impl.h:1167-1187); not the [`EC-23`](ec_23_datacopypad_ub_gm_crashes_on_ascend950pr_507035.md) V351 direction-restriction surface — the primitive is absent outright, and there is no SIMT fallback. Any A5 kernel using pad copies needs a dav-m200 copy strategy: plain `DataCopy` with 256B-quantum counts + in-kernel ragged tail (CAND-DAV-M200-RAGGED-TAIL-IN-KERNEL). celu 310p 2026-08-06. Cross-ref [`EC-23`](ec_23_datacopypad_ub_gm_crashes_on_ascend950pr_507035.md), [`PB-22`](pb_22_mte2_datacopy_on_v220_cann_9_0_0_has_32_byte_8_fp3.md), [`OL-167`](ol_167_datacopy_count_form_silently_truncates_non_32b_ali.md), [`PB-106`](pb_106_torch_npu_dispatcher_ops_and_a_raw_aclrt_launch.md). `applies_to: soc=Ascend310P3 (dav-m200, __CCE_AICORE__=200); cann=9.0.0; bisheng=n/a; op_class=all`
`verified_on: soc=Ascend310P3; cann=9.0.0 (SDK header CANN 安装树内 impl/dav_m200/kernel_operator_data_copy_impl.h:1167-1187, both directions)`
`unverified_on: soc=Ascend310B, Ascend910 (other 220x-family SoCs — DataCopyPad support differs per-SoC; EC-23/PB-22 evidence is V351/220x, not dav-m200)`

**Symptom**: an A5 (V351) kernel that uses `DataCopyPad` for ragged GM↔UB transfers cannot be ported to Ascend310P3 as-is — the pad API does not exist functionally on dav-m200 in either direction (GM→UB or UB→GM). This is NOT the EC-23 surface (V351 UB→GM-direction crash); on dav-m200 the primitive is absent outright.

**Mechanism**: the dav-m200 SDK data-copy implementation header marks both `DataCopyPad` directions `ASCENDC_REPORT_NOT_SUPPORT` (CANN 安装树内 impl/dav_m200/kernel_operator_data_copy_impl.h:1167-1187). dav-m200 has no pad-capable copy engine path; there is also no SIMT fallback on this SoC.

**Mitigation**: plain `DataCopy` with 256B-quantum (64 fp32) counts + an in-kernel ragged tail for `totalNum % 64` — see CAND-DAV-M200-RAGGED-TAIL-IN-KERNEL (`patterns/unverified/candidates.md`) and PB-106 for why the tail must be in-kernel rather than host-staged. Counts aligned by construction → PB-22's 32B-alignment constraint is satisfied structurally, with zero padding buffers.

**Evidence**: celu 310p port (2026-08-06) — A5 archive kernel used pad-free copies already; the port confirmed at the SDK header level that no `DataCopyPad` fallback exists on dav-m200 and shipped the in-kernel tail pattern instead. Pass A 5/5 OVERALL_T1, det 5/5.
  - diag_v2 310p port (2026-08-09, second instance): upstream's `IsDataCopyPadSupport` guard fails at `__CCE_AICORE__==200` — the API exists in the catalog for other chips, so check the guard BEFORE designing the copy path. Shipped a fully-aligned 64×64 diagonal-block strided `DataCopy` (blockCount=rows, blockLen=64B, dstStride=(width−64)B — aligned iff width%32==0 AND colBase%32==0) with per-element aligned 32B read-modify-write as the unaligned fallback. 8/8 bit-exact T1, det 8/8.
  - reflection_pad1d_v2 310p port (2026-08-10, third instance — live-probed REFINEMENT, flagged not auto-resolved): the classic non-Ext `DataCopyPad` is declared for `__CCE_AICORE__=200` and COMPILES, and GM→UB actually WORKS on device despite the header NOT_SUPPORT marking above; UB→GM also compiles but its writes SILENTLY never land in GM (canary probe: kernel runs, args arrive, scalar GM writes land, DataCopyPad UB→GM data absent — no error raised). So on dav-m200 the failure mode is worse than NOT_SUPPORT for the UB→GM direction: silent data loss, not a report. The `DataCopyPadExtParams`/`DataCopyExtParams` forms are 3510/5102-only in this SDK (CANN 安装树内 kernel_operator_data_copy_intf.h:385-391), so the Ext substitute is unavailable on m200. Practical ruling: UB→GM DataCopyPad = forbidden (silent-broken); GM→UB works but is vendor-unsupported — prefer plain `DataCopy` in both directions.
