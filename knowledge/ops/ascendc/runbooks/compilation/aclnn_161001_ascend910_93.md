# ACLNN 161001 — ascend910_93 缺算子内核配置

## 现象

在 Ascend910B (npu-smi 显示 Ascend910, chip 8/9) 上, 用标准 CANN 算子包格式 (op_host + op_kernel + op_api) 实现 Conv2D 算子, CANN 9.0.0, 构建并安装算子包后, 用 aclnn 测试程序调用 `aclnnConv2DGetWorkspaceSize` 时, 该 API 直接返回错误码 161001, kernel 根本未执行。测试用例为 FP16 basic 配置 (N=1, CIn=4, HIn=8, WIn=8, COut=8, KH=3, KW=3, stride=1, pad=1)。算子包是用 `build.sh` 构建的, 该脚本把 `ASCEND_COMPUTE_UNIT` 仅设为 `ascend910b`。构建日志显示只安装了 `kernel/config/ascend910b/conv2_d.json` 与 `kernel/config/ascend910b/binary_info_config.json`, 没有 `ascend910_93` 对应的配置目录。

## 适用场景

- **工程形态**: aclnn 调用 + 标准 CANN 算子包 (op_host/op_kernel/op_api), 经 `build.sh` + cmake + `-DASCEND_COMPUTE_UNIT=...` 构建算子 run 包。
- **API 路径**: `aclnnConv2DGetWorkspaceSize` → 运行时按 socVersion 匹配 `binary_info_config.json`; `op_host/*_def.cpp` 的 `AICore().AddConfig(...)` 注册可用的 soc 配置; CMakeLists 的 `ASCEND_COMPUTE_UNIT` 变量决定实际编译哪些 soc 的 kernel 二进制。
- **验证过的平台与 CANN 版本**: Ascend910B (socVersion `ascend910_93`, NpuArch `DAV_2201`), CANN 9.0.0。frontmatter `platforms: [a2]` 与此一致。
- **适用粒度**: `platform_wide` — 同 SoC 变体 (ascend910_93 / ascend910b 同属 DAV_2201) 的所有自定义算子包构建均受此约束。
- **路线优先级**: `recommended_fastpath` — 为设备实际上报的每个 socVersion 显式 AddConfig 并在构建时显式列出, 是默认推荐做法。
- **明确不适用或未验证场景**: 非 DAV_2201 架构 (如 Ascend910A / a3 / 950) 的 soc 注册行为未在本轨迹验证; 950/a3 平台是否同样需要逐 soc 变体 AddConfig 未验证 (推断可迁移, 见 `## 失效边界`)。

## 根因

运行时 aclnn 框架按设备上报的 socVersion (`ascend910_93`) 精确匹配算子包内 `kernel/config/<soc>/binary_info_config.json`; `ascend910_93` 与 `ascend910b` 虽同属 NpuArch `DAV_2201` (同一硬件代), 但 socVersion 字符串不同, 框架不做架构级回退。当算子包只注册/构建了 `ascend910b` 时, 设备上报 `ascend910_93` 找不到对应配置, `binary_info_config.json of socVersion [ascend910_93] does not support opType [Conv2D]`, 于是 `aclnnConv2DGetWorkspaceSize` 直接返回 161001, kernel 不执行。这是"构建侧 compute-unit 集合 ⊊ 运行时设备 socVersion 集合"导致的配置缺失, 不是算子实现本身的 bug。

## 判别方法

**触发**: `aclnnConv2DGetWorkspaceSize` 返回 161001 (非 0 退出, kernel 未跑)。

**可执行探针**: 检查 plog 与构建产物两处。
1. plog 检索 (本轨迹实际执行的命令, verbatim):
```bash
cat /home/developer/ascend/log/debug/plog/plog-<pid>_<ts>.log 2>/dev/null | \
  grep -i -E "ERROR|conv2|Conv2D|161001|tiling|infer|fail|not found|shape" | head -30
```
预期命中行: `binary_info_config.json of socVersion [ascend910_93] does not support opType [Conv2D]` (该 plog 错误串在本轨迹中由 reasoning 转述; 重复复现时以 plog 实测输出为准)。

2. 检查算子包安装目录是否含设备 socVersion 对应的 kernel/config 子目录:
```bash
find <vendor>/op_impl/ai_core/tbe/kernel/config/ -maxdepth 1 -type d
```
若只列出 `ascend910b` 而设备上报 `ascend910_93`, 即为配置缺失。

**原始观测**: 构建安装日志 (本轨迹 tool_observed, verbatim 节选) 仅出现:
```
-- Installing: .../kernel/config//ascend910b
-- Installing: .../kernel/config//ascend910b/conv2_d.json
-- Installing: .../kernel/config//ascend910b/binary_info_config.json
-- Installing: .../config/ascend910b/aic-ascend910b-ops-info.json
```
无 `ascend910_93` 行 — 配置缺失在产物层即可证实, 不必依赖 plog。

**解释**: `ascend910_93` 是 `ascend910b` 的一个 soc 变体 (同一 NpuArch `DAV_2201`), 但运行时按 socVersion 精确匹配, 不做架构级回退。`build.sh` 把 `COMPUTE_UNIT` 硬编码为 `ascend910b` 单值, 与 `CMakeLists.txt` 中默认的 `set(ARCH32_COMPUTE_UNITS ascend910b ascend910_93)` 不一致, 导致只编译了 ascend910b 一份 kernel 二进制与配置。

## 预防

- 在 `*_def.cpp` 的 `AICore()` 链上, 为目标设备会上报的**每个** socVersion 显式 `.AddConfig("<soc>")` (参考 hardSwish8 同时 `.AddConfig("ascend910b").AddConfig("ascend910_93")` 的写法)。
- `build.sh` 不要把 `ASCEND_COMPUTE_UNIT` 硬编码为单一 soc; 用分号列表 (`ascend910b;ascend910_93`) 或直接不覆盖 CMakeLists 的默认 `ARCH32_COMPUTE_UNITS`。
- 构建后用上面的 find 探针核对 `kernel/config/` 下是否含设备 socVersion 子目录, 再安装。

## 验证信号

- `aclnnConv2DGetWorkspaceSize` 返回 161001, 测试程序 Aborted (FP16 basic 用例, N=1 CIn=4 HIn=8 WIn=8 COut=8 KH=3 KW=3)（来源平台：a2；证据等级: tool_observed）。
- 首次构建安装产物仅含 `kernel/config/ascend910b/` (conv2_d.json + binary_info_config.json + aic-ascend910b-ops-info.json), 无 `ascend910_93` 目录（来源平台：a2；证据等级: artifact_verified）。

## 失效边界

- 950 (Ascend950) 与 a3 (Ascend910A) 平台的 soc 注册行为未在本轨迹验证; 推断同样需要逐 soc 变体 AddConfig (因 aclnn 框架的 socVersion 精确匹配机制是跨架构通用的), 但**未验证, 推断可迁移**。
- 若设备的 socVersion 恰好等于构建时注册的唯一 soc (例如老款 Ascend910B 上报 `ascend910b`), 则不会触发 161001 — 这会掩盖配置缺失, 导致开发者误以为算子包已正确支持该平台, 迁移到上报 `ascend910_93` 的同代芯片时才暴露。
