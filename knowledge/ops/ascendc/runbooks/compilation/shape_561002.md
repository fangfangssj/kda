# 标量输入被赋非标量 shape 致 561002 判别

## 现象

AscendC 算子 `lars_v2_update`（Ascend950，CANN 9.0.0）黑盒全量用例首次执行几乎全部 NO_OUTPUT——单用例日志显示 `aclnnLarsV2Update execute failed: errno[561002] OpName:[LarsV2Update_0] LarsV2Update do tiling failed, ret is -1. ... Check NnopbaseExecutorDoTiling(executor) failed`。golden 独立验证正常（返回正确 shape/dtype 的 torch.Tensor），所以不是 golden 问题，是被测 kernel 在设备 tiling 阶段失败、未产出输出。

根因排查发现：spec.yaml 明确规定 `w_square_sum` / `g_square_sum` / `weight_decay` / `learning_rate` 的 `role: scalar`（synthesize shape 为 `[]`/`()`/`(1,)`），但黑盒用例 gen_data 把这些标量输入赋了非标量大形状（如一维大 shape），违反 spec role:scalar，导致 host `TilingFunc`（`PadAndSqueeze`/`CheckBroadcastShape`）无法处理 → tiling 失败 → 561002 → NO_OUTPUT。

## 适用场景

- **工程形态**：AscendC aclnn 通路算子的黑盒精度执行（host `TilingFunc` + 设备 tiling + aclnn execute）。
- **API 路径**：spec.yaml `role: scalar` + `synthesize` shape 声明；host `TilingFunc`（`PadAndSqueeze`/`CheckBroadcastShape`）；aclnn `aclnnLarsV2Update` execute → `NnopbaseExecutorDoTiling`。
- **验证过的平台与 CANN 版本**：Ascend950，CANN 9.0.0。
- **适用粒度**：`operator_family`——任何在 spec 里声明 `role: scalar` 输入、host TilingFunc 按标量语义处理 shape 的 AscendC 算子。
- **路线优先级**：`diagnostic_only`——本卡只给判别方法与根因解释；修复实现的终版代码（标量输入 shape 改为 `[]`/`[1]`）未从 trace 逐字恢复。
- **不适用或未验证场景**：输入本就是张量、spec 未声明 role:scalar 的算子；a2/a3 未验证。

## 根因

spec.yaml 把 `w_square_sum`/`g_square_sum`/`weight_decay`/`learning_rate` 声明为 `role: scalar`，并给出 `synthesize: {w_square_sum.shape: "[]"}` 等标量形状。host `TilingFunc` 按标量语义实现 `PadAndSqueeze`/`CheckBroadcastShape`（标量广播到 w 的 shape）。当黑盒用例 gen_data 给这些输入赋了非标量大形状（如一维大 shape），`TilingFunc` 在处理该 shape 时无法走通标量广播路径 → `NnopbaseExecutorDoTiling` 返回 -1 → 设备 tiling 失败 → errno 561002 → kernel 无输出 → NO_OUTPUT。大量用例高度一致地 NO_OUTPUT 说明是系统性 shape 不符，不是个别 kernel 计算缺陷。

机制链：spec role:scalar（约束）↔ 用例 gen_data 给非标量大 shape（违反约束）↔ host TilingFunc 标量语义处理失败 ↔ 设备 do tiling ret -1 ↔ 561002 ↔ NO_OUTPUT。

## 判别方法

**触发条件**（tool_observed 失败症状）：黑盒全量执行出现大批 NO_OUTPUT（无输出），单用例日志含 `errno[561002] ... do tiling failed, ret is -1 ... NnopbaseExecutorDoTiling(executor) failed`。

**可执行探针**：
1. 读 spec.yaml，列出所有 `role: scalar` 的输入及其 `synthesize` shape。
2. 读黑盒用例 CSV/gen_data，检查这些标量输入实际被赋的 shape。
3. 比对——若标量输入被赋了非 `[]`/`[1]` 的形状，即为根因。
4. 对照实验：golden 独立验证是否正常（排除 golden 侧），归一化只改 attributes key/bool 是否影响张量输入（排除执行配置侧）。

**原始观测**（Ascend950，CANN 9.0.0，lars_v2_update 黑盒执行）：
- 黑盒全量执行几乎全部 NO_OUTPUT，且高度一致；golden 独立验证正常（排除 golden 侧）。
- 单用例日志定位到 `do tiling failed`（不是计算错、不是 shape 推导输出错，是 tiling 阶段失败）。

**机制解释**（根因分析，属 interpretation）：spec 声明标量、TilingFunc 按标量实现，用例给非标量 shape 违反约束 → TilingFunc 标量语义处理失败 → `NnopbaseExecutorDoTiling` 返回 -1 → 561002 → NO_OUTPUT。判别核心是 spec role 与用例 shape 的不一致，而非 kernel 计算链缺陷。

## 预防

- 黑盒用例 gen_data 必须读 spec.yaml 的 `role` 与 `synthesize` shape，对 `role: scalar` 输入只赋 `[]`/`[1]`（或 `()`）形状。
- 黑盒用例生成后跑一轮 shape 合规校验：标量输入的 shape 不得 >1 维、不得含 >1 元素。
- 不要把 561002 当 kernel 实现缺陷去改 kernel 计算链——先核 spec role 与用例 shape 是否一致。

## 验证信号

- spec.yaml 规定 `w_square_sum`/`g_square_sum`/`weight_decay`/`learning_rate` 的 `role: scalar`，`synthesize` shape 为 `[]`/`(1)`（来源平台：Ascend950；证据等级：artifact_verified）
- LOG.md 04:38 黑盒执行条目落地：全量跑黑盒用例，大量 NO_OUTPUT=kernel tiling 失败(561002)，根因用例标量输入 wss/gss/wd/lr 给非标量大形状违反 spec role:scalar（来源平台：Ascend950；证据等级：tool_observed）

## 失效边界

- Ascend950 实测；a2/a3 未验证，推断可迁移（TilingFunc 标量语义与 spec role 跨平台一致），标注"未验证，推断可迁移"。
- 仅适用 spec 声明 `role: scalar` 的输入；若算子输入本就是张量、TilingFunc 按 shape 处理，561002 须另查（如 tiling 切分越界、workspace 超额等）。

## 坏实践

- 看到 561002 就去改 kernel 计算链或 TilingFunc 公式，不先核 spec role 与用例 shape 一致性。
- 把大量 NO_OUTPUT 标"已知问题/环境问题"放行通过——这是反投机取巧的"标注放行"捷径，掩盖用例 gen_data 缺陷。

## 误诊

- 无明显误诊路径；排查较早排除了 golden 问题（golden 独立正常）与执行配置问题（归一化只改 attributes key/bool 不影响张量输入），直接定位到 kernel tiling 失败 + spec role 不符。
