# count超4096仅前4288元算正确的精度阈值

## 现象

在 Ascend950PR（DAV_3510 / arch35）上开发的逐元素融合算子（`fused_mul_apply_momentum`，后迁移到 ops-math），ST L0 验收（40 例）以 92.5% 通过后进入 TTK 批跑（240 例 + TF Golden）。批跑中出现一个与数据规模相关的精度阈值：

- `256x1`、`256x4` 的 FP16 用例 100% 通过；
- `256x64` FP16 仅 26.5% 正确、`256x256` FP32 仅 26.48% 正确、`512x512` FP16 仅 21.56% 正确——**FP32 也失败**，说明问题与 FP16 Cast 路径无关，而与张量第二维（inner_count）大小相关。

用 `debug_ic_test.csv` 扫 inner_count，得到精确阈值表：

| inner_count | count (a_i × inner_count) | 结果 | 正确率 |
|-------------|---------------------------|------|--------|
| 16 | 4096 | PASS | 100% |
| 17 | 4352 | FAIL | 98.53%（1.47% 正确） |
| 18 | 4608 | FAIL | 93.06%（6.94% 正确） |
| 19 | 4864 | FAIL | 88.16%（11.84% 正确） |
| 20 | 5120 | FAIL | 83.75%（16.25% 正确） |

关键观测：**正确率 × count 恒等于 4288**（4352×0.9853≈4288, 4608×0.9306≈4288, 4864×0.8816≈4288, 5120×0.8375≈4288）。即无论 count 多大，只有前 4288 个元素被正确处理，其余全部错误。

dump 分析（输入形状 (256,17)=4352 元素）：不匹配从 `linear_idx=4288` 开始，对应位置 (252, 4)，`4288 = 256×16 + 128`——前 16 行正确，第 17 行（最后一行）起出错。同期 tiling 数据显示 `a_i=256, a_o=0`（应为 1）、`max_bro_shape=[1,0]`（应为 [256,17]），tiling 解析/传递疑似异常。

## 适用场景

- 工程形态：kernel 直调 + aclnn ST（ops-registry-invoke 工作流产物，后用 ops-migrate2builtin 迁移到 ops-math）。
- API 路径：自定义 NDDMA 广播搬运 `CopyInBrc` + `AscendC::Cast/Mul/Muls/Add/Sub`；tiling 由 `op_host/arch35/*_tiling_arch35.cpp` 的 `DoTilingAndSet`/`FindSplitAxis` 产出。
- 验证过的平台与 CANN 版本：Ascend950PR（DAV_3510 / arch35），CANN 9.0.0，vendor=`custom_math`。仅 950 实测。
- 适用粒度：`operator_family`——判别规则适用于任何使用 NDDMA 广播 CopyInBrc + per-tile count 的逐元素融合算子，不限于本算子。
- 路线优先级：`safety_fallback`——本卡是诊断判别而非修复配方；定位到 4288 不变量后应回 tiling/CopyInBrc 机制层修复，不要直接套用 batch-split（见 `## 坏实践`）。
- 不适用或未验证场景：count≤4096 不触发；a2/a3 未验证（推断可迁移，见 `## 失效边界`）。

## 判别方法

**触发条件**（tool_observed）：逐元素融合算子在 Ascend950 上出现「部分 case 错、特定 shape 错、count 越大正确率越低」的 `partial_case_mismatch`，且 FP32 与 FP16 同时受影响。

**可执行探针**（本 trace 实际执行过）：

1. 固定第一维、扫第二维大小，定位阈值：
   ```bash
   cd <ttk-workdir> && python3 -m ttk kernel \
     -i debug_ic_test.csv \
     --plugin <op>/<op>_golden.py \
     --output debug_ic_result.csv -d --pc=1 --proc-no-run=0
   ```
   构造 `debug_ic_test.csv`，shape 取 `(256, inner_count)`，inner_count 从 1 扫到 20。

2. 对每个 case 计算 `正确率 × count`，检验是否为常数。若是精确常数 N，则「只有前 N 个元素正确」。

3. dump 失败 case 的输入/输出/golden 为 npy，定位首个不匹配的 linear_idx：
   ```bash
   python3 -m ttk kernel -i debug_ic_failed_only.csv \
     --plugin <op>_golden.py \
     --dump-on-fail --dump-format npy
   ```
   把 linear_idx 拆成 `行×行宽 + 列`（如 4288 = 256×16 + 128），判断「前若干行正确、尾行出错」。

4. 同步 dump tiling 参数（`a_i / a_o / max_bro_shape`），若 `a_o=0` 或 `max_bro_shape` 缺维，指向 host 侧 tiling 传递而非 kernel 计算逻辑。

**原始观测**（来源平台：Ascend950；证据等级: tool_observed）：

- inner_count=16/count=4096 100% 通过；17 起 98.53% 失败、正确率随 inner_count 线性下降（来源平台：Ascend950；证据等级: tool_observed）
- 正确率 × count = 4288 精确常数，四个 case 全部吻合到整数（来源平台：Ascend950；证据等级: tool_observed）
- 不匹配首位置 linear_idx=4288 = 256×16+128，前 16 行正确、第 17 行出错（来源平台：Ascend950；证据等级: tool_observed）
- FP32 与 FP16 均出现同样阈值，与 dtype 无关（来源平台：Ascend950；证据等级: tool_observed）
- tiling `a_o=0 / max_bro_shape=[1,0]` 异常（来源平台：Ascend950；证据等级: tool_observed）

**解释（interpretation，未确认）**：4288 是「实际被正确处理的元素数」上界。三种候选机制均未在本 trace 内证实：(a) 某 AscendC API（Cast/Muls/Add/Sub/Copy）对 count 有 ~4096/4288 的硬限制——查文档只找到 `repeatTimes<256`，未找到 4288；(b) `CopyInBrc` 内 `params.loopInfo.loopSize[nd] = a_i_seg` 决定 NDDMA 单次复制元素数，a_i_seg 与 batch_count 混用可能导致只搬前若干元素；(c) tiling `a_o=0 / max_bro_shape=[1,0]` 传递错误导致 kernel 只处理首 tile。三者中 (c) 与 dump 观测（a_o=0、max_bro_shape 缺维）最吻合，但未做对照实验确认。根因未追到底，三种候选机制均未被对照实验证实。

## 验证信号

本 trace 内验证仅达诊断层（确认了 4288 不变量与首错位置），未达修复验证层：

- inner_count=16/count=4096 100% 通过（来源平台：Ascend950；证据等级: tool_observed）
- 正确率 × count = 4288 跨四个 case 精确常数（来源平台：Ascend950；证据等级: tool_observed）
- 首个不匹配 linear_idx=4288=256×16+128（来源平台：Ascend950；证据等级: tool_observed）
- FP32 与 FP16 同阈值，与 dtype 无关（来源平台：Ascend950；证据等级: tool_observed）
- tiling a_o=0/max_bro_shape=[1,0] 异常（来源平台：Ascend950；证据等级: tool_observed）
- batch-split 修复未上板（kernel 二进制时间戳未更新），无修后信号（来源平台：Ascend950；证据等级: tool_observed）

## 失效边界

- count≤4096（inner_count≤16）不触发本现象。
- 平台：仅 Ascend950PR 实测。a2/a3 未验证，推断可迁移（同 arch 的 NDDMA/tiling 行为应一致，但 4288 这个具体常数是否同值未验证）。
- 若根因最终落在 host 侧 tiling 传递（`a_o=0`），则与平台无关、与算子家族的 tiling 实现强相关。

## 坏实践

- **batch-split 绕过（banned）**：尝试「将大 count 拆成多个 ≤4096 的小批次」修改 `ProcessStandardFp16`/`ProcessNesterovFp16` 的批量循环、按 `batch_count / inner_dims` 重算 `batch_a_i_seg`。该路线 banned，理由有二：(1) 未实际验证——写入 kernel 后重建安装，但 vendor 目录下 kernel 二进制时间戳仍为 Jul 21 21:01，而修复写入于 Jul 22 17:25，`build_out/*.run --install-path` 未更新 kernel 二进制，batch-fix 从未上板，用户确认「现象仍然没有改变，仍然是只对了 4288 个元素」，本 trace 内 batch-split 的 efficacy 未知；(2) 即便生效也只是绕过——batch-split 不解释「为何恰好 4288」，只把大 count 切小，真正的机制层根因（tiling 传递 / NDDMA loopSize / API count 限制）仍需定位。修复代码的 verbatim before/after 未在本 trace 中恢复（转写截断），不得用示意片段绕过。
- **未校验 kernel 二进制就下结论「修复无效」**：batch-fix 后跑 TTK 仍见 4288，一度怀疑修复方向错误，最后才发现是 `--install-path` 没更新 vendor 目录下的 `.o`。下次先 `ls -l` 核对 kernel 二进制时间戳再下任何「修复无效」结论。

## 误诊

- 假设「AscendC API 对 count 有 4096 限制」，但本 trace 观测到的是 4288 而非 4096，且文档中未找到 4288 限制（来源平台：Ascend950；证据等级: agent_reported）——此假设未证实，不应作为根因引用。
- 假设「问题与 FP16 Cast 路径有关」，被 256x256 FP32 同样 26.48% 失败的观测推翻。

## 预防

- TTK 批跑设计必含「固定一维、扫另一维」的 size-sweep 用例，能在验收前暴露 count 阈值类问题。
- 任何「修复后跑测试现象不变」时，第一步核对 kernel 二进制时间戳与 vendor 安装路径，排除「修复未上板」。
