# 对齐补齐的通道被当作地址使用时是越界风险，不是数值风险

## 已有结论的覆盖范围

"向量长度按 `AlignUp32` 上取整分配、但 GM 访问只按**真实**元素数（`DataCopyPad(blockLen=k_len*4)`）"
这条已被广泛使用，它保护的是**数值正确性**：多算出来的通道留在自己的缓冲里，不写回 GM。

姊妹卡 `runbooks/compilation/507035_gather_l2_offset_overread` 覆盖的是 **offset buffer
分配不足 256B 时 Gather 整寄存器越界读**；本卡是它的对偶——**buffer 分配够、但对齐尾部
未初始化**同样被解引用，两者共享"Gather 会消费整个对齐宽度"这一根因，修法不同
（前者补足分配，本卡要求尾部清零）。

## 它没有覆盖的一种消费方式

当那段**被多算出来的补齐通道**不是当作**数据**、而是当作**地址**被消费时，上面的保护不成立：

```
Gather(dst, src, offsetTensor, ...)
```

`offsetTensor` 的补齐通道里是**未初始化字节**，会被当成偏移**解引用**。
后果是 **UB 内越界访问 / fault 风险**，不是"某几个数算错"——而"限制 GM 访问范围"那条建议
**够不到这里**，因为危险发生在 UB 侧。

## 判别

问一句：这条向量的**消费者**是把它当**数值**还是当**地址/索引**？
只要出现 `Gather`/间接寻址/`offset` 语义，补齐通道就必须有确定值。

## 缓解

kernel 入口对 offset/weight 类向量的**完整对齐范围**做一次性清零，之后按真实长度计算。
row34 实测：该 op 50 例中有相当比例（case 4/12/15/20/21/36/40…）的 `k_len = crop_w*c`
不是 fp32 8 元素粒度的整数倍，最终 **50/50 PASS，36/50 逐字节相等**。

## 边界

单算子实测（gather 类）。可迁移的是**"按消费者语义区分补齐通道的危险类型"**这条判别，
不是具体 case 列表。
